# 한계와 다음 스텝

- **작성일**: 2026-08-12

이 문서는 **이 PoC가 증명하지 못한 것**을 적는다.
잘 된 것만 적으면 검증이 아니라 홍보다.

---

## 1. 가장 큰 한계 — 평가 음성이 합성이다

### 1.1 무엇이 문제인가

평가에 쓴 20건은 전부 **TTS로 합성한 음성**이다. 실제 어르신의 발화가 아니다.
합성 음성은 진짜 고령 화자 음성과 다음이 다르다.

| 항목 | 실제 고령 화자 | 이 PoC의 합성 음성 |
|---|---|---|
| 발음 명료도 | 치아 상태·구강 근력에 따라 흐려짐 | 항상 또렷함 |
| 음성 떨림(振顫) | 흔함 | 없음 |
| 방언 억양 | 지역에 따라 강함 | 표준 억양 |
| 말 더듬·수정 | 잦음 | 대본대로만 |
| 발화 속도 변화 | 문장 안에서도 들쭉날쭉 | 균일 |
| 녹음 환경 | 마이크 거리·반향 제각각 | 균일 |

속도를 늦추고(`-30%`) 피치를 낮추고(`-15Hz`) 생활 소음을 섞어
근사치를 만들었지만, **이건 어디까지나 흉내다.**

### 1.2 그래서 어떤 주장이 약해지는가

- ❌ **"실제 어르신 음성에서 CER 1.84%가 나온다"** — 이렇게 말할 수 없다
- ⭕ **"같은 음성에 두 방식을 돌렸을 때 이런 차이가 났다"** — 이건 말할 수 있다

즉 이 PoC가 만든 것은 **절대 성능의 근거가 아니라 상대 비교의 근거**다.
그리고 애초 목적이 "교체할지 판단할 근거"였으므로, 그 목적에는 부합한다.

### 1.3 왜 실데이터를 안 썼는가 (그리고 이건 타협이 아니다)

실사용자 음성은 가족의 실제 대화다. 공개 저장소에 올라가는 순간 되돌릴 수 없다.
**이 제약은 우회해야 할 장애물이 아니라 이 도메인의 본질**이고,
바로 그 제약이 "로컬로 내리자"는 개선 방향을 만들어냈다
([problem-statement.md](problem-statement.md) §2 문제 2).

실데이터를 못 쓰는 것이 문제라면, 그 문제를 없애는 게 이 PoC의 결론이다.

### 1.4 어떻게 보완할 수 있나

| 방법 | 장점 | 비용 |
|---|---|---|
| 본인·가족이 **동의 하에** 대본을 낭독해 녹음 | 진짜 사람 음성 | 시간, 그리고 저장소에는 못 올림 |
| 공개 고령 화자 음성 코퍼스 확보 | 재현 가능 | 한국어 고령 화자 공개셋이 드묾 |
| 실서비스에서 **CER 없이** 실패율만 집계 | 실사용 데이터 | 정답 전사문이 없어 CER은 못 잼 |

세 번째가 현실적인 다음 수순이다. **정답이 없어도 "전사 실패율"과
"사용자가 되묻는 비율"은 잴 수 있고**, 그것만으로도 교체 효과를 확인할 수 있다.

## 2. 특이사항 추출 점수는 과대평가다

### 2.1 무엇이 문제인가

S5 재현율이 1.000으로 나왔다. **이 숫자를 그대로 믿으면 안 된다.**

**대본을 쓴 사람과 추출 규칙을 쓴 사람이 같다.**
어떤 문장이 들어올지 알면서 규칙을 만들었으니, 잘 맞는 게 당연하다.
전형적인 과적합이고, 처음 보는 발화에서는 이 점수가 나올 리 없다.

### 2.2 규칙 기반의 구조적 한계

| 한계 | 예시 |
|---|---|
| 사전에 없는 표현은 못 잡음 | "삭신이 쑤신다", "밥맛이 뚝 떨어졌어" 같은 변형 |
| 방언 어휘 미지원 | "허리가 애린다"(경상), "다리가 저릿저릿허다"(전라) |
| 맥락 이해 없음 | "약 먹었냐고? 먹었지 뭐" 같은 되받아치기 |
| 반어·농담 구분 못 함 | "죽겠네 아주" (관용 표현인지 실제 호소인지) |
| 정도(severity) 판단 없음 | "좀 아프다"와 "너무 아프다"를 구분하지 않음 |

### 2.3 그럼에도 규칙 기반을 택한 이유

LLM을 붙이면 위 한계 상당수가 풀린다. 그런데 **클라우드 LLM을 쓰면
전사에서 막은 외부 전송이 이 단계에서 도로 뚫린다.** 전사문은 음성보다
오히려 더 노골적인 개인정보다. 그건 이 PoC의 전제를 스스로 무너뜨리는 일이다.

그래서 지금은 규칙 기반으로 두고, 확장 방향을 아래 §5에 남겼다.

## 3. 측정 자체의 한계

### 3.1 표본이 작다

합성 20건(2.4분) + 공개셋 40건(6.8분). **통계적으로 결론 내기엔 적다.**
CER 차이가 몇 %p 수준이면 표본 오차와 구분되지 않는다.
큰 차이(예: 2배 이상)만 유의미하게 읽어야 한다.

### 3.2 정규화가 완벽하지 않다

숫자 표기 차이를 없애려고 아라비아 숫자를 한글 읽기로 바꿨지만,
**고유어 수사(하나·둘·셋…여든)는 처리하지 못한다.**

실제로 이런 사례가 나왔다.

| 정답 | 인식 결과 | 실제 판정 | 문제 |
|---|---|---|---|
| 새벽 **세시** | 새벽 **3시** | 오류로 계산됨 | 사람이 보기엔 맞는 전사 |
| **여든 일곱** 채 | **87**채 | 오류로 계산됨 | 사람이 보기엔 맞는 전사 |

즉 **측정된 CER은 실제보다 나쁘게 나온 값**이다.
다만 두 시스템 모두 같은 방식으로 불이익을 받으므로 **비교의 공정성은 유지**된다.

### 3.3 Zeroth-Korean은 도메인이 다르다

공개셋은 **뉴스 낭독체**다. 고유명사와 숫자가 많고, 어르신 일상 대화와 문체가 전혀 다르다.
이 데이터의 CER은 "일반 한국어 기준선"으로만 읽어야 하고,
**돌봄 대화 성능의 근거로 쓰면 안 된다.**

### 3.4 지연시간은 이 기계에서만 유효하다

측정에 쓴 환경은 GPU 없는 8코어 CPU다. 다른 기계에서는 다른 수치가 나온다.
또 클라우드 방식의 지연시간에는 **네트워크 왕복과 그날의 서버 혼잡도**가 섞여 있어,
모델 자체의 속도 비교로 읽으면 안 된다.

## 5. 추가 시도 — 실제로 한 것

과제 안내의 "조금 더 발전시키고 싶다면" 항목을 **제안이 아니라 실행**으로 채웠다.
결과는 아래와 같고, 각각 별도 문서에 근거가 있다.

| 항목 | 한 것 | 결과 | 문서 |
|---|---|---|---|
| **파이프라인 확장** | STT → 추출 → 로컬 TTS 음성 리포트, 사진 처리(YOLO+SAM), 회상 이미지(Diffusion) | 5개 모델 전부 로컬 CPU 동작 | [evaluation.md](evaluation.md) §7~9 |
| **파인튜닝 대체** | 도메인 어휘 프롬프트 + 공개셋 교차 검증 | CER **-28.8%**, 과적합 설정 1개 적발 | [tuning.md](tuning.md) |
| **데모 배포** | Gradio 웹 앱 (3탭) | 동작 화면 캡처 3장 | [../README.md](../README.md) §4 |
| **실패 케이스 정리** | 나쁜 입력 10종 강건성 테스트 | 환각 0건, **결함 5개 발견 → 4개 수정** | [failure-cases.md](failure-cases.md) |

### 그중 가장 값진 것 — 교차 검증이 잘못된 결정을 막았다

합성 데이터에서 CER을 41.3% 줄인 설정이 **실제 사람 음성에서는 20.7% 악화**됐다.
합성 데이터만 보고 결정했다면 실서비스를 나쁘게 만들 뻔했다.

> 성능을 올리는 것보다, **올렸다고 착각하지 않는 것**이 어려웠다.

## 5-1. 아직 남은 다음 스텝

아래는 **우선순위 순**이다.

### 5.1 [1순위] 실패율 기반 실서비스 검증

정답 전사문 없이도 잴 수 있는 것부터 잰다.

- 전사 실패율 (기존 방식은 이걸 아예 안 남기고 있었다)
- 사용자가 되묻는 비율 ("뭐라고?", "못 알아들었어") — 전사 품질의 간접 지표
- 무음 응답 비율

**이건 실데이터 없이도, 저장소에 아무것도 올리지 않고도 할 수 있다.**
그래서 1순위다.

### 5.2 [2순위] 파이프라인 확장 — 다중 모델 연결

지금은 `STT → 추출` 2단이다. 여기에 이미 로컬에서 돌고 있는 TTS를 붙이면
**음성으로 받아 음성으로 답하는 완전 로컬 루프**가 된다.

```
음성 입력 → Whisper(STT) → 특이사항 추출 → 응답 생성 → 로컬 TTS → 음성 출력
   ↑                                                              ↓
   └──────────────  전 구간 로컬. 외부 전송 0건  ──────────────────┘
```

TTS는 이미 로컬에서 무료로 돌고 있으므로, STT만 내리면 루프가 닫힌다.
**이 PoC가 그 마지막 조각이다.**

### 5.3 [3순위] 로컬 소형 LLM으로 추출 단계 교체

규칙 기반의 한계(§2.2)를 풀되 외부 전송은 유지하지 않는 방법.

- 로컬에서 도는 소형 LLM으로 특이사항 추출을 대체
- 규칙 기반 결과를 정답 삼아 비교 → 어느 쪽이 나은지 실측
- 규칙 기반을 **안전망으로 남겨두고** LLM 결과와 합집합을 쓰는 방식도 가능

### 5.4 [4순위] 진짜 파인튜닝

**하이퍼파라미터 조정은 이미 했다** (→ §5 표, [tuning.md](tuning.md)).
`initial_prompt`로 CER 28.8%를 줄였고, `beam_size`·VAD·앞문맥 참조도 모두 측정했다.

남은 것은 **가중치를 실제로 학습시키는 파인튜닝**이다.
한국어 고령 화자 음성으로 Whisper를 추가 학습하면 도메인 성능이 더 오를 수 있다.

그러나 §1.3의 데이터 문제가 그대로 걸린다. 학습에는 도메인 음성이 필요한데
그게 바로 안 쓰기로 한 데이터다. **동의 기반 자체 녹음이 쌓인 뒤에나** 착수할 수 있다.

아직 안 해본 무학습 조정도 남아 있다.

- 어휘 목록 확장 (16개 → 30~50개). 단, 너무 길면 프롬프트가 전사에 새어나올 위험
- `temperature` 폴백 전략
- 화자별 개인화 프롬프트

### 5.5 [5순위] 데모 배포 — 부분적으로 함

**Gradio 웹 앱을 만들었다** (`app.py`, 3탭). 로컬에서 `python app.py`로 띄운다.

아직 안 한 것은 **인터넷 배포**다. 그리고 이건 미룬 게 아니라 **의도적으로 안 한 것**이다.

배포하는 순간 사용자가 올린 파일이 서버로 전송된다.
"음성·사진이 기기 밖으로 나가지 않는다"는 이 PoC의 전제와 정면으로 충돌한다.

그래서 앱 화면 상단에 경고를 고정으로 띄운다.

> ⚠️ 실제 가족의 음성·사진을 올리지 마세요.
> 이 화면은 저장소에 들어 있는 합성 샘플을 시연하기 위한 것입니다.
> 실사용은 각자의 기기에서 로컬 실행이 전제입니다.

공개 배포를 한다면 **합성 샘플만 다루는 시연용**임을 명확히 하고,
업로드 기능을 아예 막고 예제만 돌리게 하는 편이 원칙에 맞다.

## 6. 결론 — 이 PoC로 무엇을 말할 수 있고 없는가

### 말할 수 있는 것 ⭕

- 로컬 Whisper는 GPU 없는 이 환경에서 **실시간보다 빠르게** 돈다
- 어르신 발화 특성(느린 말·침묵·소음)을 흉내낸 음성에서 **무너지지 않았다**
- 외부 전송 **0건**, 비용 **0원**은 구조적으로 보장된다 (측정이 아니라 정의)
- 전사 실패를 **원인별로 분류해 남길 수 있다** — 기존 방식은 이걸 못 했다
- 전사 뒤에 추출 단계를 붙이면 **대화에 묻히던 신호를 꺼낼 수 있다**
- 나쁜 입력(무음·소음·손상 파일)에서 **환각 0건** — 없는 말을 지어내지 않았다
- 학습 없이 **CER 28.8% 개선**이 가능하다는 것, 그리고 **교차 검증 없이는
  그 개선이 진짜인지 알 수 없다**는 것
- **5개 모델(STT·TTS·탐지·분할·생성) 전부 GPU 없이** 한 대에서 돈다는 것
- 알약 세기를 **정답 있는 벤치마크로 재면 상대오차 3.0%** (떨어뜨려 놓은 경우)
- 전사의 구두점 오류가 후단을 깨뜨릴 수 있다는 것, **그리고 그 취약점이 고쳐진다는 것**
  ([failure-cases.md](failure-cases.md) §5)
- **로컬 모델은 같은 입력에 같은 출력을 낸다** — 두 번 돌린 결과가 해시까지 일치했다.
  같은 기간에 **클라우드 쪽은 그렇지 않았다** ([evaluation.md](evaluation.md) §6.2).
  성능을 재려면 먼저 **잴 수 있어야** 하는데, 그 조건부터 갈렸다

### 말할 수 없는 것 ❌

- 실제 어르신 음성에서의 정확도
- **기존 방식과의 정확도 우열** — 기준선을 두 번 돌렸더니 CER이 0.0075와 0.0185로 달라
  **한 번은 지고 한 번은 이겼다.** 어느 쪽이 정확하다고 말할 근거가 없다
  ([evaluation.md](evaluation.md) §6.2)
- **그 변동이 왜 생겼는지** — 모델 교체 쪽에 무게가 실리지만 표본 4건으로는 단정 못 한다
- 장기간 운영했을 때의 안정성
- 특이사항 추출이 처음 보는 표현에서도 통한다는 것
- 겹쳐 쏟아진 알약을 셀 수 있는지
- 이 개선이 실서비스에서 실제로 체감될 것이라는 것

### 그래서 결론은

> **교체를 검토할 근거는 만들어졌다. 교체를 확정할 근거는 아직 아니다.**
>
> 다음 수순은 §5.1 — 실데이터를 저장소에 올리지 않고도 실서비스에서
> 실패율을 재보는 것이다.

마지막으로, 이 PoC에서 가장 많이 배운 것은 성능 수치가 아니라
**측정을 의심하는 법**이었다.

- 합성 데이터 1등이 실제 음성에서 꼴찌였다 → 교차 검증이 막았다
- 알약 세기 오차 24%의 범인은 모델이 아니라 오염된 배경이었다
- 블러를 걸었는데 얼굴이 보였다 → 눈으로 확인하지 않았으면 몰랐다
- 벤치마크에서는 빠른 모델이 데모에서는 10배 느렸다 → 실제 화면을 만들어야 보였다

**숫자가 좋게 나왔을 때 한 번 더 의심하는 것**이 이 PoC의 실제 산출물이다.
