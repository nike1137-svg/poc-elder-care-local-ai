# 실패 사례 — 어디서 무너지는가

- **작성일**: 2026-08-12
- **재현**: `python src/robustness_test.py`

잘 되는 입력만 넣어보는 것은 검증이 아니다.
이 문서는 **일부러 무너뜨려서 찾아낸 것들**을 기록한다.

기존 실서비스의 가장 큰 문제가 정확히 이 지점이었다 —
전사 실패를 빈 문자열로 뭉개서, **실패했다는 사실조차 남지 않았다.**

---

## 1. 강건성 테스트 설계

실서비스에 실제로 들어올 법한 나쁜 입력 10가지를 만들었다.

| 케이스 | 만든 것 | 현실의 상황 |
|---|---|---|
| `silence` | 무음 5초 | 어르신이 잘못 눌러 녹음됨 |
| `tiny` | 0.1초 | 손이 미끄러져 바로 뗌 |
| `noise_only` | 소음만 6초 | TV만 켜진 방 |
| `loud_noise` | 말소리 + 큰 소음 | 시끄러운 곳에서 녹음 |
| `clipped` | 문장 중간 잘림 | 전송 중 끊김 |
| `very_quiet` | -30dB | 마이크에서 멂 |
| `wrong_lang` | 영어 발화 | `language=ko` 고정의 부작용 확인 |
| `empty_file` | 0바이트 | 전송 실패 |
| `corrupt` | 헤더 손상 | 파일 깨짐 |
| `not_audio` | 텍스트 파일 | 잘못된 첨부 |

---

## 2. 결과 요약

| 구분 | 건수 | 내용 |
|---|---:|---|
| 깨끗하게 걸러짐 | **6** | 실패를 실패로 보고했다 |
| **환각** | **0** | 없는 말을 지어내지 않았다 |
| 품질 저하 관찰 | 4 | 처리는 됐고 결과를 기록했다 |

### 환각이 0건인 것이 가장 중요하다

무음과 소음만 있는 입력에서 **아무 말도 만들어내지 않았다.**
이게 중요한 이유는, 만약 없는 말을 지어냈다면
그 뒤의 특이사항 추출이 **존재하지 않는 건강 신호를 보호자에게 보고**했을 것이기 때문이다.

> "어르신이 오늘 무릎이 아프다고 하셨습니다" — 실제로는 TV 소리만 녹음된 파일에서.

이런 일이 한 번이라도 나면 시스템 전체의 신뢰가 무너진다.

## 3. 발견 ① — 무음 입력에서 44초가 걸렸다 (수정 완료)

### 증상

| 입력 | 지연 |
|---|---:|
| 정상 발화 (5초) | 2.90s |
| **무음 (5초)** | **44.20s** |
| **소음만 (6초)** | **37.20s** |

정상 발화보다 **15배 느렸다.** Whisper는 알아들을 게 없으면 오히려 더 오래 헤맨다.

실서비스에서 어르신이 실수로 빈 녹음을 보내면 파이프라인이 44초간 멈춘다.
그 사이 다음 메시지도 밀린다. 장애로 이어질 문제였다.

### 원인

Whisper는 입력에 음성이 있는지 없는지 **모르는 채로** 디코딩을 시작한다.
무음에서는 무엇을 내놓을지 확신하지 못해 반복적으로 탐색하다가 결국 빈 결과를 낸다.
그 헛수고에 시간이 다 든다.

### 수정 — VAD를 '분할'이 아니라 '관문'으로

VAD(음성 구간 검출)로 음성을 잘라내면(`vad_filter=True`) 속도는 빨라진다.
그러나 **어르신의 긴 침묵이 발화 끝으로 오인되어 뒷말이 잘릴 위험**이 있다
([model-selection.md](model-selection.md) §5.1).

그래서 VAD를 전사에 쓰지 않고, **전사 전에 "말소리가 하나라도 있는가"만 묻는 관문**으로 썼다.

```
음성 입력 → [VAD 관문] 말소리 있나?
              ├ 없음 → 즉시 NO_SPEECH 로 실패 보고 (0.1초)
              └ 있음 → VAD 없이 통째로 전사 (침묵 보존)
```

### 수정 효과

| 케이스 | 수정 전 | 수정 후 | 배수 |
|---|---:|---:|---:|
| silence | 44.20s | **0.09s** | **470배** |
| noise_only | 37.20s | **0.07s** | **510배** |
| 정상 발화 | 2.90s | 3.05s | 관문 비용 +0.15s |
| **테스트 전체** | **97.9s** | **20.8s** | **4.7배** |

정상 입력에 0.15초를 더 쓰는 대신, 쓰레기 입력에서 44초를 0.09초로 줄였다.
**실패 분류도 `empty_output` → `no_speech`로 바뀌어 원인이 더 정확해졌다.**

## 4. 발견 ② — 도메인 프롬프트의 부작용

[tuning.md](tuning.md)에서 채택한 도메인 어휘 프롬프트를 켠 뒤,
**한국어가 아닌 입력에서 거동이 나빠졌다.**

| | 프롬프트 없음 | 프롬프트 켬 (채택 설정) |
|---|---|---|
| 영어 발화 | `안녕하세요,This is a test sentence in English, not Korean` | `안녕하세요, 한국인은 영어로 말하는 것입니다` |
| 판정 | 원문을 그런대로 옮김 | **없는 한국어 문장을 지어냄** |

한국어 어휘로 편향시켜 놓았으니 예상 가능한 결과다.
`language="ko"` 고정과 겹쳐 효과가 커졌다.

**실서비스 영향은 낮다** — 입력이 항상 한국어이기 때문이다.
그러나 CER 28.8% 개선이 **공짜가 아니었다**는 사실은 기록해둔다.

> 교훈: 성능을 올리는 조정은 대개 어딘가를 대가로 치른다.
> 어디를 치렀는지 모르면 올린 게 아니라 옮긴 것이다.

## 5. 발견 ③ — 전사의 구두점 오류가 후단을 깨뜨렸다 (수정 완료)

### 증상

특이사항 추출 재현율이 **정답 전사문 기준 1.000인데 STT 출력 기준 0.960**으로 떨어졌다.
놓친 것은 `u16`의 기분 신호였다.

| | 텍스트 |
|---|---|
| 정답 | 어지러워서 오늘은 그냥 **누워 있었어.** 일어나면 핑 돌더라고. |
| Whisper 출력 | 어지러워서 오늘은 그냥 **누워. 있었어.** 일어나면 핑 돌더라고. |

Whisper가 "누워 있었어"에 **없는 마침표를 찍었고**, 추출기가 문장을 거기서 쪼개는 바람에
`누워 있었` 패턴이 매칭되지 않았다.

### 원인

추출기가 **ASR이 만들어낸 구두점을 신뢰**하고 문장을 나눴다.
구두점은 화자가 말한 것이 아니라 모델이 지어낸 것인데도.

### 수정

문장 단위 검사에 더해 **구두점을 걷어낸 전체 텍스트로도 한 번 더** 훑도록 했다.

| | 수정 전 | 수정 후 |
|---|---:|---:|
| STT 출력 기준 재현율 | 0.960 | **1.000** |
| 정밀도 | 0.962 | 0.962 (변화 없음) |

**오탐 증가 없이** 취약점이 사라졌다.

## 6. 발견 ④ — 측정값이 나쁠 때 모델보다 데이터를 먼저 의심하라

알약 세기 벤치마크에서 **거의 모든 케이스가 정확히 +1개씩** 과다 집계됐다.
정답이 1개인 이미지에서도 2개가 나왔다.

무작위 오차가 아니라 체계적 편향이었으므로 원인이 하나라는 뜻이었다.

### 원인 — 배경이 오염되어 있었다

벤치마크 배경으로 **알약 사진의 구석을 잘라 썼는데, 거기에 원본 알약이 남아 있었다.**
모델이 그 알약을 정확히 찾아낸 것이다. 모델은 잘못한 게 없었다.

### 수정 — 물체가 없는 배경을 따로 생성

SD-Turbo로 `"empty wooden table, nothing on it"`을 생성해 배경으로 썼다.

| 지표 | 오염된 배경 | 깨끗한 배경 |
|---|---:|---:|
| 정확히 맞춤 | 1/6 | **5/7** |
| ±1개 이내 | 5/6 | **7/7** |
| 평균 절대 오차 | 1.00개 | **0.29개** |
| 평균 상대 오차 | 24.0% | **3.0%** |

**대조군(빈 테이블)도 정확히 0개**로 나왔다 — 배경만으로는 오검출이 없다.

## 7. 발견 ⑤ — 데모 화면에서 드러난 모델 재적재 낭비

웹 데모에서 인물 마스킹을 돌리자 **YOLO 탐지 6.0초, SAM 분할 16.3초**로 찍혔다.
CLI에서 잰 값(0.14초 / 1.6초)의 10배가 넘었다.

차이는 전부 **모델 적재 시간**이었다. 사진 한 장 처리할 때마다
가중치를 디스크에서 다시 읽고 있었다.

### 수정 — 프로세스당 1회 적재

| | 첫 호출 | 이후 호출 |
|---|---:|---:|
| YOLO | 11.18s | **0.084s** (133배) |
| SAM | 2.35s | **1.46s** |

> 이건 모델 성능 문제가 아니라 **구현 문제**였다.
> 벤치마크만 돌렸다면 못 찾았을 것이다. 실제로 쓰는 화면을 만들어봐야 보인다.

## 8. 아직 남아 있는 실패

수정하지 않았거나 수정할 수 없는 것들.

### 8.1 잘린 오디오는 잘린 대로 나온다

| | 텍스트 |
|---|---|
| 원본 | 오늘은 무릎이 좀 시큰거려서 산책은 못 나갔다 |
| 2초에서 자름 | 오늘은 무릎이 시큰거리다 |

**뒤를 지어내지 않은 것은 좋다.** 다만 "산책을 못 나갔다"는 신호가 사라져
특이사항 추출이 통증만 잡고 활동 제한은 놓친다.

전송 중 끊김은 STT가 해결할 수 있는 문제가 아니다.
메신저 계층에서 재전송으로 다뤄야 한다.

### 8.2 아주 작은 목소리도 통과했다 (예상 밖)

-30dB로 줄인 음성이 **정확히 전사됐다.** 예상보다 강건했다.
다만 실제 원거리 녹음은 단순 볼륨 감소가 아니라 반향·잡음이 섞이므로,
이 결과를 "멀리서 말해도 된다"로 읽으면 안 된다.

### 8.3 특이사항 추출은 사전에 없는 표현을 못 잡는다

규칙 기반의 구조적 한계다. "삭신이 쑤신다", "밥맛이 뚝 떨어졌어" 같은 변형이나
방언 어휘("허리가 애린다")는 사전에 없으면 놓친다.
자세한 논의는 [limitations.md](limitations.md) §2.

### 8.4 알약이 겹쳐 있으면 못 센다

벤치마크는 알약을 서로 떨어뜨려 배치했다. 실제로는 겹쳐 쏟아지는 경우가 많고,
그때는 SAM이 하나로 묶거나 잘못 나눈다. 실사진 3장에서 후보 수가
54 / 50 / 5로 나왔지만 **정답이 없어 정확도를 말할 수 없다.**

## 9. 이 절에서 얻은 것

발견 다섯 가지 중 **네 가지가 수정으로 이어졌다.**

| 발견 | 조치 | 효과 |
|---|---|---|
| 무음에서 44초 | VAD 관문 추가 | 470배 단축 |
| 구두점 오류로 신호 누락 | 구두점 불신 처리 | 재현율 0.96 → 1.00 |
| 배경 오염으로 +1 과다 집계 | 깨끗한 배경 생성 | 상대오차 24% → 3% |
| 모델 재적재 낭비 | 프로세스당 1회 적재 | 133배 단축 |
| 도메인 프롬프트 부작용 | (수정 안 함, 기록만) | 실서비스 영향 낮음 |

> 테스트를 안 만들었다면 **네 가지 모두 실서비스에서 터졌을 것**이다.
> 그중 둘(무음 44초, 모델 재적재)은 성능 장애로,
> 하나(신호 누락)는 조용한 오작동으로 나타났을 것이다.
