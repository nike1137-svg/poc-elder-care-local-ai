# 문제 정의서 — 고령 부모 돌봄 대화 어시스턴트의 음성 인식 개선

- **작성일**: 2026-08-12
- **과제**: Main Quest 2 — 내 도메인에서 AI로 개선 지점 찾아서 PoC 만들기
- **다루는 모델**: 음성인식(STT)

---

## 0. 이 문서를 읽기 전에 — 데이터 취급 원칙 ★

이 저장소는 **실제 서비스의 코드도, 실제 사용자의 음성도 담고 있지 않다.**

내가 운영 중인 실서비스는 고령의 가족과 매일 나누는 대화를 다룬다. 대화 내용 그 자체가
이 도메인에서 가장 민감한 자산이고, 공개 저장소에 올라가는 순간 되돌릴 수 없다.
GitHub는 커밋 히스토리에 남고, 지워도 포크·캐시·인덱싱이 남는다.

그래서 이 PoC는 다음 원칙 위에서 만들어졌다.

| 원칙 | 구체적 조치 |
|---|---|
| 실서비스 코드 미포함 | 실서비스를 참조하되, PoC는 이 저장소에서 처음부터 새로 작성 |
| 실사용자 음성 미포함 | 평가용 음성은 전량 **합성 대본 기반**으로 새로 제작 |
| 개인 식별 정보 미포함 | 대본의 인물·지명·병명은 모두 가공 |
| 도메인 설명은 추상화 | 실서비스명·내부 구조·가족 신상 미기재 |

### ★ 대체된 것은 데이터뿐, 파이프라인은 실서비스 그대로다

오해를 막기 위해 분명히 해둔다. **바꾼 것은 평가용 데이터셋 하나뿐이다.**

| 항목 | 실서비스 | 이 PoC |
|---|---|---|
| 입력 오디오 형식 | m4a (AAC / 16kHz / 모노) | **동일** |
| 처리 대상 | 메신저가 넘겨준 오디오 파일 | **동일한 형식의 파일** |
| 도메인 어휘 | 혈압약·경로당·무릎… | **실제 도메인에서 그대로 가져옴** |
| 개선 대상 지점 | 실제 운영 코드의 전사 호출 | **그 코드를 직접 읽고 특정함** |
| 평가용 음성 | 어르신의 실제 발화 | **창작 대본 → 합성** ← 여기만 다르다 |

즉 파이프라인은 실서비스가 받는 것과 **똑같은 형식의 입력**을 받아 처리한다.
개선할 지점도 상상해서 만든 게 아니라 **돌아가는 코드를 읽고 찾았다.**
합성으로 대체한 것은 **성능을 재기 위한 평가 표본**이다.

> **이것은 과제 요건을 비켜간 것이 아니라, 이 도메인을 이해했기 때문에 내린 판단이다.**
> 과제 안내에도 "개인정보를 다룰 때는 보안을 주의하세요"라고 명시되어 있다.
> 실데이터를 못 쓰는 제약 자체가 이 도메인의 핵심 성질이고,
> 그 제약이 **개선 방향을 결정했다** (→ §3, §4). 자세한 논의는 [limitations.md](limitations.md).

## 1. 도메인 설명 — 어떤 업무·현장·관심 영역인가

**고령의 부모와 떨어져 사는 가족을 위한, 메신저 기반 일상 대화 어시스턴트.**

멀리 사는 자식이 매일 안부를 묻기는 어렵다. 전화는 서로 부담이고, 문자는 어르신이 치기 힘들다.
그래서 메신저 봇이 매일 말을 걸고, 어르신은 **음성 메시지로 답한다.**
봇은 그 답을 알아듣고 대화를 이어가고, 필요하면 음성으로 되말한다.

### 1.1 왜 음성인가

이 도메인에서 음성은 편의 기능이 아니라 **유일하게 성립하는 입력 수단**이다.

- 70대 이상 사용자에게 스마트폰 타이핑은 진입장벽 1순위다
- 손 떨림·노안으로 작은 키보드는 오타를 양산한다
- 반면 "말하기"는 평생 해온 일이라 학습이 필요 없다

즉 **STT가 뚫리지 않으면 이 서비스는 입력 자체가 성립하지 않는다.**
STT는 이 도메인의 부가 기능이 아니라 관문이다.

### 1.2 현재 파이프라인 (실서비스, 개념 수준)

```
어르신이 음성 메시지 전송
   → 메신저 플랫폼에서 오디오 파일(m4a) 수신
   → base64 인코딩
   → 클라우드 범용 LLM(멀티모달)에 오디오 + "이 음성을 한국어 텍스트로 변환해주세요" 프롬프트 전송
   → 응답 텍스트를 전사 결과로 사용
   → 대화 생성 로직에 투입
   → 응답 문장 생성
   → TTS 서비스(로컬 프로세스 → 외부 엔진 호출)로 음성 합성 → 어르신에게 전달
```

여기서 짚어야 할 사실이 하나 있다. **음성 루프의 양쪽이 모두 외부로 나간다.**

| 방향 | 엔진 위치 | 비용 | 음성·텍스트 외부 전송 |
|---|---|---|---|
| 나가는 음성 (TTS) | **외부 (edge-tts / Microsoft)** | 0원 | **있음** |
| 들어오는 음성 (STT) | **외부 (클라우드 LLM)** | 호출당 과금 | **있음** |

TTS는 로컬 서버 프로세스로 떠 있지만, 그 프로세스가 하는 일은
**합성할 텍스트를 외부 TTS 서비스로 보내고 음성을 받아오는 것**이다.
"서버가 내 컴퓨터에 있다"와 "연산이 내 컴퓨터에서 일어난다"는 다르다.

정리하면 지금은 이렇다.

- 어르신이 **말한 내용**(음성)이 밖으로 나간다 → 유료
- 어르신에게 **들려줄 내용**(텍스트)도 밖으로 나간다 → 무료

둘 다 개인적인 대화다. 민감도로 치면 어르신이 실제로 말한 음성 쪽이 더 높으므로
이번 PoC는 **STT부터** 손댄다. 다만 목표는 한쪽만 막는 게 아니라
**음성 루프 전체를 집 안으로 들이는 것**이고, 그 첫 조각이 STT다.

> **자기 점검 ★** — 이 PoC의 평가용 음성도 edge-tts로 합성했다.
> 공교롭게 실서비스와 같은 엔진·같은 화자(`ko-KR-SunHiNeural`)다.
> 평가 입력을 만드는 용도라 측정의 공정성에는 영향이 없지만,
> "합성 음성이라 쉬웠던 것 아니냐"는 반론의 근거가 되므로
> 실제 사람이 읽은 공개 데이터셋으로도 함께 측정했다 ([evaluation.md](evaluation.md)).

## 2. 현재의 문제 — 지금은 어떻게 하고 있고, 어떤 부분이 번거롭고 비효율적인가

### 문제 1. 전용 음성인식 모델이 아니라, 범용 LLM에게 받아쓰기를 "부탁"하고 있다

현재 전사는 ASR(자동음성인식) 전용 모델이 아니라, 범용 멀티모달 LLM에 오디오를 넣고
자연어 프롬프트로 "한국어 텍스트로 변환해주세요"라고 요청하는 방식이다.

동작은 한다. 그러나 구조적으로 다음이 보장되지 않는다.

- **출력이 전사인지 요약인지 보장되지 않는다.** 프롬프트 기반이라 모델이 말을 줄이거나
  다듬어 버릴 수 있다. ASR 모델은 애초에 받아쓰기만 하도록 학습되어 그런 여지가 없다
- **정확도가 측정된 적이 없다.** 지금까지 이 도메인에서 문자오류율(CER)을 잰 기록이 없다.
  "대충 되는 것 같다" 수준으로 운영되고 있다
- **어르신 발화에서 어떻게 깨지는지 모른다.** 느린 발화, 방언 억양, 웅얼거림, 문장 중간의
  긴 침묵 — 고령 화자 음성의 전형적 특성에 대해 이 방식이 강한지 약한지 근거가 없다

### 문제 2. 유료 경로이면서, 무료 대안을 쓸 수 없는 딜레마에 갇혀 있다

이 항목은 이미 내부적으로 **미결정 과제로 올라와 있던 사안**이다.

- 클라우드 STT의 **무료 티어는 입력 데이터가 모델 학습에 활용될 수 있다.**
  가족의 실제 대화를 다루므로 **무료 티어는 애초에 선택지가 아니다**
- 그렇다고 유료 티어를 쓰면 **대화가 오갈 때마다 과금이 붙는다.**
  매일 쓰는 서비스라 호출량이 사용 빈도에 정비례해 늘어난다

즉 **"공짜로 쓰면 프라이버시가 깨지고, 프라이버시를 지키면 돈이 든다"**는 구조에 갇혀 있다.
이 딜레마는 클라우드에 음성을 보내는 한 해소되지 않는다.

### 문제 3. 전사 실패를 조용히 삼킨다

현재 구현은 전사 호출이 실패하면 **빈 문자열로 대체하고 그대로 진행한다.**

그 결과:

- 어르신은 분명히 말씀을 하셨는데, 봇은 아무 말도 못 들은 것처럼 반응한다
- 어르신 입장에서는 **"얘가 내 말을 씹었다"**로 체감된다. 신뢰가 깨지는 지점이다
- 실패가 로그로 남지 않아 **얼마나 자주 실패하는지조차 모른다**
- 네트워크 오류인지, 오디오 형식 문제인지, API 한도인지 구분이 안 된다

측정되지 않는 실패는 개선될 수 없다.

### 문제 4. 전사 이후가 없다 — 중요한 신호가 대화 속에 묻힌다

전사된 텍스트는 대화 생성 로직으로 바로 들어가고, 그것으로 끝이다.

그런데 이 도메인에서 대화의 진짜 가치는 **대화 그 자체가 아니라 거기 섞여 나오는 신호**다.

> "오늘은 무릎이 좀 시큰거려서 산책은 못 나갔어"
> "약은… 아침에 먹었나 모르겠네"
> "요새 입맛이 통 없어"

이런 문장들은 대화 흐름 속에서는 스쳐 지나가지만, 떨어져 사는 가족에게는
**가장 알고 싶은 정보**다. 지금은 이게 어디에도 정리되지 않는다.
가족이 알려면 대화 로그를 처음부터 끝까지 직접 읽어야 하는데, 매일 그럴 사람은 없다.

## 3. 개선 가설 — AI를 어떤 단계에 어떻게 넣으면 나아지는가

> **가설:** 클라우드 범용 LLM 프롬프트 전사를,
> **로컬에서 도는 ASR 전용 모델(Whisper 계열)** 로 교체하고
> 그 뒤에 **특이사항 추출 단계**를 붙이면,
> 정확도를 유지하거나 개선하면서 **비용을 0원으로, 외부 데이터 전송을 0건으로** 만들 수 있다.

### 3.1 개선 후 파이프라인

```
어르신 음성 메시지 (m4a)
   → [기존] 클라우드 LLM 프롬프트 전사        ← 유료 · 외부 전송 · 실시간 초과(RTF 1.82)
   → [개선] 로컬 Whisper 계열 ASR 전사        ← 0원 · 외부 전송 없음 · CER 측정됨
        ↓
   → [신규] 특이사항 추출 (건강 / 기분 / 복약 / 식사)
        ↓
   → 구조화된 결과 출력 (전사문 + 특이사항 목록)
```

### 3.2 이 가설이 각 문제를 어떻게 푸는가

| 문제 | 개선안이 푸는 방식 |
|---|---|
| 1. 범용 LLM으로 받아쓰기 | 받아쓰기만 하도록 학습된 ASR 전용 모델로 교체. CER로 정확도를 실측 |
| 2. 유료 ↔ 프라이버시 딜레마 | **로컬 실행이 딜레마 자체를 없앤다.** 음성이 기기 밖으로 나가지 않으므로 학습 활용 우려도, 과금도 성립하지 않는다 |
| 3. 실패를 삼킴 | 실패를 빈 문자열로 뭉개지 않고 원인별로 분리해 남긴다 |
| 4. 신호가 묻힘 | 전사 뒤에 추출 단계를 붙여 구조화된 형태로 뽑아낸다 |

특히 **문제 2가 이번 개선의 핵심**이다. 정확도가 비슷하기만 해도
"돈 안 들고 + 데이터가 밖으로 안 나간다"는 것만으로 교체할 이유가 충분하다.
정확도까지 오르면 그건 덤이다.

### 3.3 왜 지금 이걸 하는가

기존 방식이 당장 고장 난 것은 아니다. 그런데 이 서비스는 **매일 쓰이고, 계속 쓸 것이다.**

- 호출량은 시간에 비례해 누적된다 → 비용 문제는 시간이 갈수록 커진다
- 외부 전송은 한 번이라도 잘못되면 되돌릴 수 없다 → 리스크는 줄여둘수록 좋다
- 현재 사용 중인 클라우드 모델은 **이미 신규 사용자에게 제공이 중단됐다**
  → 어차피 한 번은 갈아타야 한다. 그때 클라우드에서 클라우드로 옮기느니 로컬로 내리는 편이 낫다

> **★ 이 항목은 PoC 도중에 사실로 확인됐다.**
> 기준선을 측정하려고 실서비스와 같은 모델(`gemini-2.5-flash`)을 호출했더니
> **404와 함께 "신규 사용자에게 더 이상 제공되지 않는다"는 응답**이 돌아왔다.
> "언젠가 갈아타야 한다"가 아니라 **이미 갈아타야 하는 상태**였던 것이다.
> 로컬 모델은 한 번 받으면 이런 일정에 끌려다니지 않는다.

즉 이건 "언젠가 해야 할 교체"이고, 지금이 근거를 만들어둘 시점이다.

## 4. 대상 사용자 — 누가 이 개선으로 가장 도움을 받는가

| 순위 | 사용자 | 무엇이 나아지는가 |
|---|---|---|
| 1 | **떨어져 사는 가족 (= 나 자신)** | 대화 로그를 다 읽지 않아도 특이사항만 추려 볼 수 있다. 매달 나가던 API 비용이 사라진다. "가족 대화가 외부 서버로 나간다"는 찜찜함이 없어진다 |
| 2 | **음성으로 말하는 어르신** | 전사 실패로 말이 씹히는 일이 줄어든다. 자기 말이 제대로 전달된다는 감각이 유지된다 |
| 3 | 같은 구조를 쓰려는 개발자 | 클라우드 STT 없이 로컬만으로 한국어 돌봄 대화를 처리할 수 있다는 근거와 수치를 그대로 가져다 쓸 수 있다 |

> 과제 안내에 "나 자신이어도 괜찮습니다"라고 되어 있고, 실제로 **1순위 수혜자는 나 자신**이다.
> 이 서비스의 운영자이자, 특이사항 리포트를 받아 볼 당사자다.

## 5. 성공 기준 — 무엇이 얼마나 좋아지면 성공인가

기존 방식(클라우드 LLM 프롬프트 전사)과 **나란히 놓고** 측정한다.

### 5.1 정량 기준

| # | 지표 | 측정 방법 | 성공 기준 |
|---|---|---|---|
| S1 | **문자오류율 (CER)** | 합성 음성 + 정답 전사문 대조 | 기존 대비 **동등 이상** (악화 폭 3%p 이내면 합격, 개선되면 초과 달성) |
| S2 | **건당 처리 시간** | 오디오 입력 → 전사 완료까지 벽시계 시간 | 실시간 대비 **1배속 이내** (30초 음성을 30초 안에 처리) |
| S3 | **건당 비용** | 호출당 과금액 | **0원** (로컬 실행이므로 정의상 달성. 기존 방식과 금액 대비로 제시) |
| S4 | **외부 전송 건수** | 처리 중 발생하는 외부 네트워크 요청 수 | **0건** |
| S5 | **특이사항 추출 재현율** | 대본에 심어둔 신호를 몇 개 잡아내는가 | 심어둔 신호의 **70% 이상** 포착 |

**S1이 가장 중요하다.** S3·S4는 로컬 실행을 택한 시점에 구조적으로 달성되므로,
실제로 검증해야 할 것은 "그 대가로 정확도를 얼마나 잃는가"이다.
잃는 게 없거나 적으면 이 교체는 정당화된다.

### 5.2 정성 기준

| # | 항목 | 확인 방법 |
|---|---|---|
| Q1 | 어르신 발화 특성에 대한 강건성 | 느린 발화·침묵·방언 억양 샘플에서 두 방식의 출력을 나란히 비교 |
| Q2 | 전사 vs 요약 오염 | 기존 방식이 말을 줄이거나 다듬는 사례가 있는지 확인 |
| Q3 | 실패 사례 | 어떤 입력에서 무너지는지 수집해 기록 (숨기지 않고 남긴다) |

### 5.3 성공으로 치지 않는 것

- 실서비스에 실제로 배포되는 것 → **이번 범위 밖.** 이 PoC의 목표는 교체 판단 근거를 만드는 것까지다
- 모든 발화를 완벽히 전사하는 것 → 목표가 아니다. **기존 방식과의 상대 비교**가 목표다
- 특이사항 추출의 의학적 정확성 → **진단이 아니다.** 가족이 한 번 더 들여다볼 거리를 만드는 수준이면 충분하다
