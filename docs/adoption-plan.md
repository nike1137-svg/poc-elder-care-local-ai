# 실서비스 도입 제안서 — PoC에서 실제 적용까지

- **작성일**: 2026-08-12
- **대상**: 운영 중인 고령 부모 돌봄 대화 어시스턴트 (메신저 봇)
- **전제**: **실서비스다.** 어르신이 실제로 쓰고 있으므로 무중단·되돌리기 가능이 최우선

---

## 0. 이 문서의 성격

PoC는 "된다"를 보였다. 이 문서는 **"어떻게 실제로 바꿀 것인가"**를 다룬다.
데이터·비용·운영 방식·전환 순서·리스크를 적는다.

⚠️ **이 문서는 제안이지 실행 계획 승인이 아니다.**
아래 단계는 각각 별도 승인을 받고 진행해야 한다.

---

## 1. 무엇을 바꾸는가

현재 파이프라인에서 **바꾸는 지점은 한 곳**이다.

```
메신저 웹훅
   → 워크플로우 엔진 (n8n)
       → 오디오 다운로드
       → [ 여기 ] 클라우드 LLM 프롬프트 전사   ← ★ 이 한 블록만 교체
       → 대화 생성
       → TTS
   → 응답 전송
```

교체 대상은 **전사 호출 한 블록**이다. 그 앞뒤(오디오 다운로드, 대화 생성)는 건드리지 않는다.
입력(오디오 바이트)과 출력(전사 텍스트)의 계약이 같으므로 **드롭인 교체**가 가능하다.

### 단계별 범위

| 단계 | 바꾸는 것 | 위험도 |
|---|---|---|
| **1단계** | STT를 로컬 Whisper로 | 낮음 (되돌리기 쉬움) |
| **2단계** | 특이사항 추출 추가 (신규 기능) | 낮음 (기존 흐름에 영향 없음) |
| 3단계 | TTS를 로컬 piper로 | 중간 (음성 품질이 바뀜 — 사용자 체감) |
| 4단계 | 사진 처리를 로컬 YOLO+SAM으로 | 중간 |
| 보류 | 회상 이미지 | 신규 기능. 수요 확인 후 |

**1·2단계만 먼저 하기를 권한다.** 3단계는 목소리가 바뀌어 어르신이 이질감을 느낄 수 있고,
그건 기술 문제가 아니라 사용자 경험 문제다.

## 2. 필요한 것 — 데이터

### 2.1 전환 자체에는 데이터가 필요 없다

Whisper는 사전학습 모델이라 **추가 학습 없이 바로 쓴다.**
PoC에서 도메인 어휘 프롬프트만으로 CER 28.8%를 개선했고, 그 어휘 목록은
개인정보가 아닌 단어 나열이다.

### 2.2 검증에는 데이터가 필요하다 — 그런데 정답 전사문 없이 하는 법

실서비스 성능을 재려면 정답 전사문이 있어야 하는데, 그걸 만들려면
어르신의 실제 음성을 사람이 듣고 받아 적어야 한다. **하지 않는다.**

대신 **정답 없이 잴 수 있는 지표**로 검증한다.

| 지표 | 재는 법 | 의미 |
|---|---|---|
| 전사 실패율 | `FailureKind` 별 집계 | 기존 방식은 이걸 아예 안 남기고 있었다 |
| 무응답 비율 | 빈 전사 결과 비율 | 어르신 말이 씹힌 비율 |
| 되묻기 비율 | "뭐라고", "못 알아들었어" 등 | 전사 품질의 간접 지표 |
| 응답 지연 | 수신 → 응답 시간 | 사용자 체감 |

**이 지표들은 대화 내용을 저장하지 않고도 집계할 수 있다.**
카운터만 올리면 된다. 이게 §5 1단계의 핵심이다.

### 2.3 저장하지 않을 것

| 항목 | 처리 |
|---|---|
| 음성 원본 | 처리 후 즉시 삭제 (현재도 동일) |
| 전사 텍스트 | 대화 생성에만 사용, 별도 보관 안 함 |
| 특이사항 | **보호자에게 전달만.** 장기 축적은 별도 결정 사항 |
| 지표 | 카운터만 (내용 없음) |

> §4 주간 리포트 기능은 며칠치 신호를 모아야 성립한다.
> **이것만은 저장이 필요하므로, 도입 시 별도 판단이 필요하다.**
> 최소한으로 하려면 "신호 유형 + 날짜"만 남기고 발화 내용은 버리면 된다.

## 3. 필요한 것 — 비용

### 3.1 절감액

현재 STT는 호출당 과금된다. 로컬로 내리면 **그 항목이 0원이 된다.**

정확한 절감액은 실제 호출량에 달려 있으므로, 아래 방식으로 산출한다.

```
월 절감액 = 월 음성 메시지 수 × 건당 STT 단가
```

⚠️ **실측 호출량을 먼저 확인해야 한다.** PoC 단계에서는 알 수 없다.
전환 전 1주일간 음성 메시지 수를 세는 것을 권한다.

### 3.2 새로 드는 비용

| 항목 | 비용 |
|---|---|
| Whisper small 모델 | 0원 (최초 1회 내려받기) |
| piper 한국어 음성 | 0원 (61MB) |
| YOLO11n / MobileSAM / FastSAM | 0원 |
| SD-Turbo | 0원 (약 2.5GB) |
| 실행 하드웨어 | **0원** (기존 서버 재사용) |
| **합계** | **0원** |

**카드 등록이 필요한 항목이 없다.** 과금 경로 자체가 생기지 않는다.

### 3.3 드는 것은 비용이 아니라 자원

| 자원 | 소요 | 비고 |
|---|---|---|
| 디스크 | 약 4GB | 모델 가중치 |
| RAM | Whisper 약 1GB / SD-Turbo 6GB | **SD-Turbo가 크다** |
| CPU | 전사 중 코어 점유 | 7초 음성당 2.7초 |

⚠️ **SD-Turbo의 RAM 6GB가 실질적 제약이다.**
기존 서버에서 다른 서비스와 함께 돌리면 메모리가 빠듯할 수 있다.
회상 이미지 기능(4단계 이후)은 이 점을 먼저 확인해야 한다.
1·2단계(STT + 추출)만이면 RAM 1GB 남짓이라 부담이 없다.

## 4. 필요한 것 — 운영 방식

### 4.1 어떻게 붙이는가

워크플로우 엔진의 코드 노드에서 로컬 전사 서비스를 HTTP로 호출하는 형태를 권한다.

```
[코드 노드] 오디오 → POST http://127.0.0.1:<포트>/transcribe → 전사 텍스트
```

이유:

- 기존 코드 노드의 구조를 최소로 바꾼다 (호출 대상 URL만 교체)
- 전사 서비스를 독립 프로세스로 두면 **모델을 상주시켜 적재 비용을 없앤다**
  (PoC에서 모델 재적재로 133배 손해 본 사례 → [failure-cases.md](failure-cases.md) §7)
- 전사 서비스만 따로 재시작할 수 있다

### 4.2 반드시 지킬 것

| 원칙 | 이유 |
|---|---|
| **`127.0.0.1`에만 바인딩** | 외부에서 접근할 이유가 없다. 노출하면 PoC의 전제가 깨진다 |
| 호스트 포트 신규 개방 금지 | 공격 표면을 늘리지 않는다 |
| 기존 서비스와 격리 | 다른 에이전트·워크플로우에 영향 0 |
| 실패 시 **명시적 오류 반환** | 빈 문자열로 삼키지 않는다. 이게 개선의 핵심 중 하나다 |

### 4.3 폴백 전략 — 이게 가장 중요하다

**로컬 전사가 실패했을 때 무엇을 하는가?**

권장: **폴백하지 않는다.** 실패를 실패로 알린다.

```
로컬 전사 실패
   → 어르신에게: "잘 못 들었어요. 다시 한번 말씀해 주시겠어요?"
   → 로그에: 실패 원인 기록
```

클라우드로 폴백하면 "음성이 밖으로 나가지 않는다"는 보장이 **조건부**가 된다.
평소엔 안 나가지만 실패할 때만 나간다면, 그건 보장이 아니다.

되묻는 것은 어르신에게 자연스러운 상호작용이고,
실패를 숨기는 것보다 훨씬 낫다.

## 5. 전환 순서

### 1단계 — 관측만 (코드 변경 없음, 위험도 0)

**목적**: 현재 상태를 숫자로 안다.

- 1주일간 음성 메시지 수, 현재 전사 실패율, 응답 지연을 집계
- **대화 내용은 저장하지 않는다.** 카운터만
- 완료 기준: 기준 수치 확보

> 이 단계 없이 전환하면 "좋아졌다"를 증명할 수 없다.

### 2단계 — 그림자 실행 (shadow, 위험도 낮음)

**목적**: 실제 트래픽에서 로컬 전사가 버티는지 본다.

- 기존 클라우드 전사를 **그대로 쓰면서**, 같은 오디오를 로컬로도 전사
- 응답에는 **기존 결과만** 사용 (로컬 결과는 버림)
- 비교하는 것: 처리 시간, 실패율, 빈 결과 비율
- **두 전사문을 사람이 비교하지 않는다** (내용을 읽지 않기 위해)
- 완료 기준: 로컬 실패율이 기존과 동등 이하, RTF < 1

⚠️ 이 단계에서는 클라우드 비용이 그대로 나가고, CPU 부하가 2배가 된다.
기간을 짧게(3~5일) 잡는다.

### 3단계 — 전환 (위험도 중간)

- 응답 경로를 로컬 전사로 바꾼다
- **클라우드 전사 코드는 지우지 않고 주석/설정으로 남긴다** (즉시 되돌리기용)
- 완료 기준: 1주일간 1단계 지표가 악화되지 않음

### 4단계 — 특이사항 추출 추가 (신규 기능)

- 전사 뒤에 추출 단계를 붙인다
- 기존 대화 흐름에는 영향 없음 (별도 출력)
- 보호자에게 어떻게 전달할지는 **별도 설계 필요** (푸시? 요약 메시지? 주기는?)

### 5단계 이후 — 선택

TTS 로컬화, 사진 처리 로컬화, 회상 이미지.
각각 §1의 위험도를 다시 평가하고 결정한다.

## 6. 되돌리기 계획

각 단계에서 문제가 생기면 어떻게 되돌리는가.

| 단계 | 되돌리는 법 | 소요 |
|---|---|---|
| 1 (관측) | 집계 중단 | 즉시 |
| 2 (그림자) | 로컬 호출 코드 제거 | 즉시 (응답 경로에 없음) |
| 3 (전환) | 호출 대상 URL을 클라우드로 되돌림 | 수 분 |
| 4 (추출) | 추출 단계 비활성화 | 즉시 |

**3단계가 유일하게 사용자에게 보이는 변경**이므로, 되돌리기를 미리 연습해두는 것을 권한다.

## 7. 리스크

| 리스크 | 가능성 | 영향 | 완화 |
|---|---|---|---|
| 실제 어르신 음성에서 CER이 나쁨 | **중** | 대화 품질 저하 | 2단계 그림자 실행에서 실패율로 조기 감지 |
| CPU 부하로 다른 서비스 지연 | 중 | 전체 응답 느려짐 | 전사 서비스에 동시 처리 수 제한 |
| 메모리 부족 (특히 SD-Turbo) | **중** | OOM | 1·2단계는 RAM 1GB. 이미지 생성은 뒤로 미룸 |
| 모델 적재 비용 누락 | 낮 | 첫 요청 지연 | 상주 프로세스로 해결 (§4.1) |
| 특이사항 오탐으로 불필요한 걱정 | **중** | 보호자 피로 | "진단 아님" 문구 필수. 근거 문장 함께 제시 |
| 특이사항 미탐으로 놓침 | **중** | 신뢰 저하 | **이 기능을 안전망으로 홍보하지 않는다** |

### 가장 큰 리스크는 기술이 아니다

**특이사항 추출을 "알아서 챙겨준다"로 받아들이는 것**이 가장 위험하다.
규칙 기반이라 못 잡는 표현이 많고([limitations.md](limitations.md) §2),
"아무 알림이 없었으니 괜찮은 것"이라고 믿으면 안 된다.

전달 문구에 반드시 넣어야 할 것:

> 이것은 대화에서 눈에 띈 것을 짚어준 것일 뿐, 빠뜨린 것이 있을 수 있습니다.
> 의학적 진단이 아닙니다.

## 8. 도입 판단 기준

아래를 만족하면 3단계 전환을 권한다.

| # | 기준 |
|---|---|
| 1 | 2단계 그림자 실행에서 로컬 전사 실패율이 기존과 **동등 이하** |
| 2 | RTF가 실사용 트래픽에서 **1 미만** 유지 |
| 3 | CPU/메모리가 다른 서비스에 영향 없음 |
| 4 | 되돌리기 절차를 실제로 한 번 연습함 |
| 5 | 실패 시 되묻는 문구가 준비됨 |

하나라도 미달이면 전환하지 않는다. **급할 이유가 없다** —
현재 방식이 고장 난 게 아니라 더 나은 방식이 생긴 것이므로.

## 9. 이 제안이 다루지 않는 것

- 특이사항의 **의학적 타당성** — 이건 개발이 아니라 의료 영역
- 보호자 알림 UX 설계 — 별도 과제
- 장기 데이터 축적 정책 — §2.3 참조, 별도 결정
- 다중 사용자 확장 — 현재는 1:1 전제

## 10. 요약

| 질문 | 답 |
|---|---|
| 무엇을 바꾸나 | 전사 호출 **한 블록** |
| 데이터가 필요한가 | **아니오** (검증도 정답 전사문 없이 가능) |
| 비용이 드나 | **0원** (오히려 절감) |
| 무엇이 드나 | 디스크 4GB, RAM 1GB(1·2단계) |
| 얼마나 위험한가 | 낮음 — 되돌리기 수 분 |
| 언제 하나 | 1·2단계는 지금 가능, 3단계는 §8 기준 충족 후 |
| 가장 큰 리스크 | 기술이 아니라 **특이사항 기능에 대한 과신** |
